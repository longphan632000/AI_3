L0112 3.1. XÂY DỰNG DIAGRAM DESIGN SKILL
L0113 Bước 3A. Tạo Skill dùng chung để tạo và chỉnh sơ đồ
L0114 Tạo: .agents/skills/diagram-design/SKILL.md
L0115 Nội dung:
L0116 ---
L0117 name: diagram-design
L0118 description: Create and refine traceable software engineering diagrams with readable, report-ready layouts.
L0119 ---
L0120 # Diagram Design Skill
L0121 ## Objective
L0122 Create UML/software design diagrams that are technically correct, traceable to approved artifacts and visually suitable for direct inclusion in the report.
L0123 ## Inputs
L0124 Read the complete approved docs/system-model.md and docs/system-model-traceability.md first, then the relevant approved requirements, use-case specifications, architecture, database design and schema. Embedded diagram images from the original DOCX are reserved for the independent comparison after the new diagram has been generated.
L0125 ## Supported diagrams
L0126 Use Case Diagram; Activity Diagram; Sequence Diagram; System Architecture Diagram; Class Diagram; ERD; AI Architecture/Data Flow Diagram.
L0127 ## Process
L0128 1. Determine the requested diagram type; read the approved system model and identify its supporting URD sections, tables and Human Gate decisions.
L0129 2. List every supported actor, action, class, entity, component and relationship for this diagram, with a source reference. Resolve nothing by guessing.
L0130 3. Create or update PlantUML source under docs/diagrams/.
L0131 4. Arrange elements into a readable layout and render when tools are available.
L0132 5. Inspect the rendered output; revise layout and render again if it is difficult to read.
L0133 6. Freeze the generated .puml and rendered PNG before viewing the corresponding original image. Then compare actors/nodes, labels, relationships, cardinalities, direction and flow order with the original figure; record every difference in docs/diagram-comparison.md.
L0134 ## Rules
L0135 - Do not invent actors, use cases, actions, classes, entities, components or relationships.
L0136 - Do not use, trace, copy or visually imitate an embedded diagram image as input to generation. The original image is only an independent check after the new source and render exist.
L0137 - When the URD text, its tables and an original figure disagree, record the exact conflict and await a Human Gate decision. Do not omit a requirement merely to match the image.
L0138 - Do not silently resolve requirements conflicts or modify approved requirements just to simplify a diagram.
L0139 - Labels must be readable; nodes/text must not overlap; connectors must not pass through nodes or text.
L0140 - Avoid connector overlap and minimize crossings; group related elements and keep sufficient spacing.
L0141 - Prefer orthogonal connectors and layout constraints/hidden links when appropriate.
L0142 - Do not place long issue notes inside a diagram when the issue is already recorded in requirements-issues.md.
L0143 - Do not claim PNG output unless rendering actually succeeded.
L0144 ## Outputs
L0145 PlantUML source files in docs/diagrams/ and matching PNG files when rendering is available.
L0146 ## Verification
L0147 Before completing, verify correctness, source traceability, completeness, readable labels, no significant overlap, minimized crossings and report-ready visual quality. After generation, compare with the original figure and state whether content, relationships and flow match; visual similarity alone is not evidence of system correctness.
L0148 3.2. XÂY DỰNG TABLE DESIGN SKILL
L0149 Bước 3B. Tạo Skill dùng chung để xây dựng bảng đặc tả
L0150 Tạo: .agents/skills/table-design/SKILL.md
L0151 Nội dung:
L0152 ---
L0153 name: table-design
L0154 description: Create and refine traceable software engineering tables from approved project artifacts.
L0155 ---
L0156 # Table Design Skill
L0157 ## Objective
L0158 Create structured, consistent and traceable software-engineering tables that can be reviewed by humans and inserted into the final report.
L0159 ## Inputs
L0160 Read only the approved artifacts relevant to the requested table: source URD, requirements, use-case specifications, architecture, class model, database design/schema, tests or review reports.
L0161 ## Supported tables
L0162 Actor specification; Use Case summary; detailed Use Case specification; requirements traceability; Class specification; data dictionary; test-case/result matrix; code-review/security finding tables.
L0163 ## Process
L0164 1. Determine the purpose and source for the table.
L0165 2. Define concise, consistent columns before filling rows.
L0166 3. Preserve existing IDs such as FR/NFR/BR/UC/AC and add source/traceability columns where useful.
L0167 4. Fill only information supported by the source; mark missing/conflicting information as PENDING or reference the issue instead of inventing a value.
L0168 5. Split very large tables by section/domain when that improves readability.
L0169 6. Save reusable Markdown tables under docs/tables/.
L0170 ## Rules
L0171 - Do not invent values, actors, permissions, requirements, relationships, data types or test results.
L0172 - Do not silently resolve conflicts.
L0173 - Keep headers consistent and avoid cells that contain unrelated information.
L0174 - Long flows should use numbered steps or dedicated sub-tables rather than one unreadable cell.
L0175 - Never mark a test/result as PASSED unless execution evidence exists.
L0176 ## Outputs
L0177 Markdown table artifacts under docs/tables/ or the table section explicitly requested by the domain Skill.
L0178 ## Verification
L0179 Verify every row is source-supported, IDs are preserved, unresolved points are visible, columns are consistent, tables are readable and suitable for Human Gate review.

L0481 # Database Design Skill
L0482 ## Objective
L0483 Transform approved requirements and architecture into a consistent,
L0484 normalized and traceable relational database design for MySQL.
L0485 The database design must support the approved business requirements
L0486 without inventing new business rules or entities.
L0487 ## Inputs
L0488 Read the following approved artifacts when available:
L0489 - docs/requirements.md
L0490 - docs/user-stories.md
L0491 - docs/acceptance-criteria.md
L0492 - docs/requirements-issues.md
L0493 - docs/architecture.md
L0494 - docs/architecture-decisions.md
L0495 - docs/diagrams/class-diagram.puml
L0496 - docs/source-urd.md
L0497 - docs/system-model.md
L0498 - docs/system-model-traceability.md
L0499 Only use decisions that have passed the relevant Human Gate.
L0500 If a required decision is still PENDING,
L0501 do not silently choose a solution.
L0502 ## Process
L0503 ### 1. Identify data domains
L0504 Identify the data groups required by the approved requirements.
L0505 For this project, verify coverage of at least:
L0506 - accounts/users;
L0507 - projects;
L0508 - project members;
L0509 - skills, availability and work capacity;
L0510 - tasks;
L0511 - sprint and milestones;
L0512 - comments and attachments;
L0513 - meeting notes and AI-generated meeting-minute drafts;
L0514 - AI requests/results/history when FR-15 is implemented;
L0515 - reports/audit logs;
L0516 - notifications if FR-16 is implemented; use the approved event, recipient, timing and data fields in docs/requirements-decisions.md.
L0517 Do not assume that one data group must correspond to exactly one table.
L0518 ### 2. Identify entities
L0519 Derive entities from the approved requirements and architecture.
L0520 For each entity identify:
L0521 - purpose;
L0522 - primary identifier;
L0523 - main attributes;
L0524 - ownership/project scope;
L0525 - lifecycle;
L0526 - relationships with other entities.
L0527 Do not create an entity only because it is technically convenient
L0528 unless it is necessary to implement an approved requirement.
L0529 ### 3. Identify relationships
L0530 Identify:
L0531 - one-to-one relationships;
L0532 - one-to-many relationships;
L0533 - many-to-many relationships.
L0534 Resolve many-to-many relationships using associative tables when needed.
L0535 Verify that relationships do not allow data from different projects
L0536 to be incorrectly linked.
L0537 ### 4. Normalize the model
L0538 Normalize the relational model to an appropriate level,
L0539 normally up to Third Normal Form (3NF).
L0540 Check for:
L0541 - duplicated data;
L0542 - repeating groups;
L0543 - partial dependencies;
L0544 - transitive dependencies.
L0545 Do not normalize in a way that changes the approved business meaning.
L0546 ### 5. Define primary and foreign keys
L0547 For every table define:
L0548 - PRIMARY KEY;
L0549 - FOREIGN KEY;
L0550 - referenced table;
L0551 - update/delete behavior when required.
L0552 Foreign keys must preserve project and ownership consistency.
L0553 ### 6. Define data types
L0554 Choose MySQL data types appropriate for each field.
L0555 Consider:
L0556 - identifiers;
L0557 - text length;
L0558 - date/time values;
L0559 - boolean/status values;
L0560 - numeric estimates and capacity;
L0561 - JSON only when relational representation is not appropriate.
L0562 Do not store passwords in plain text.
L0563 ### 7. Define constraints
L0564 Consider and document:
L0565 - NOT NULL;
L0566 - UNIQUE;
L0567 - CHECK;
L0568 - DEFAULT;
L0569 - FOREIGN KEY constraints.
L0570 Constraints must reflect approved requirements and business rules.
L0571 Examples:
L0572 - project membership must not be duplicated;
L0573 - task estimate must not be negative;
L0574 - start date must not be after end date where required;
L0575 - status values must follow approved rules.
L0576 ### 8. Define indexes
L0577 Create indexes only when they support expected queries.
L0578 Consider indexes for:
L0579 - login/email lookup;
L0580 - project_id;
L0581 - assignee_id;
L0582 - sprint_id;
L0583 - task status;
L0584 - due date;
L0585 - commonly combined filtering fields.
L0586 Avoid unnecessary indexes.
L0587 ### 9. Design AI-related data
L0588 For AI functionality, separate business data from AI execution metadata.
L0589 AI-related storage may include approved information such as:
L0590 - task type;
L0591 - requester;
L0592 - referenced project/data;
L0593 - prompt version;
L0594 - model/provider;
L0595 - generated result;
L0596 - confirmation status;
L0597 - confirmer;
L0598 - timestamps.
L0599 Never store:
L0600 - API keys;
L0601 - passwords;
L0602 - secrets.
L0603 FR-15 is Should-have and must not be treated as mandatory
L0604 unless the project has approved its implementation.
L0605 For FR-16, use the approved minimum notification fields in docs/requirements-decisions.md.
L0606 Record any newly discovered gap as an issue instead of inventing business data.
L0607 ### 10. Create ERD
L0608 Create:
L0609 docs/diagrams/erd.puml
L0610 The ERD must show:
L0611 - entities/tables;
L0612 - primary keys;
L0613 - foreign keys;
L0614 - main attributes;
L0615 - cardinality;
L0616 - major relationships.
L0617 Use diagram-design skill for layout and rendering quality.
L0618 The ERD must:
L0619 - keep related entities near each other;
L0620 - avoid overlapping entities and text;
L0621 - avoid relationship lines passing through entities or labels;
L0622 - minimize relationship crossings;
L0623 - keep PK/FK and cardinality readable;
L0624 - be suitable for direct inclusion in the report.
L0625 If the first render is difficult to read,
L0626 revise the layout and render again.
L0627 ### 11. Create SQL schema
L0628 Create:
L0629 database/schema.sql
L0630 The SQL schema must be consistent with the ERD
L0631 and database design document.
L0632 Use MySQL-compatible syntax.
L0633 Do not create sample production credentials or secrets.
L0634 ### 12. Verify traceability
L0635 Verify that:
L0636 Requirement / Business Rule
L0637 ↓
L0638 Entity / Relationship / Constraint
L0639 ↓
L0640 ERD
L0641 ↓
L0642 SQL Schema
L0643 can be traced.
L0644 Every major table or relationship must have a reason
L0645 supported by the approved project artifacts.
L0646 ## Rules
L0647 - Do not write Flask source code.
L0648 - Do not modify approved requirements.
L0649 - Do not invent business requirements.
L0650 - Do not silently resolve PENDING Human Gate decisions.
L0651 - Do not store passwords, API keys or secrets in plain text.
L0652 - Do not claim the database was executed successfully unless it was actually executed.
L0653 - Keep ERD, database-design.md and schema.sql consistent.
L0654 ## Outputs
L0655 Create or update:
L0656 - docs/database-design.md
L0657 - database/schema.sql
L0658 - docs/diagrams/erd.puml
L0659 If PlantUML rendering is available, also create:
L0660 - docs/diagrams/erd.png
L0661 ## Verification
L0662 Before completing, verify:
L0663 - all approved data domains are covered;
L0664 - every table has a clear purpose;
L0665 - primary keys are defined;
L0666 - foreign keys are valid;
L0667 - relationships and cardinalities are correct;
L0668 - normalization has been checked;
L0669 - NOT NULL / UNIQUE / CHECK constraints are appropriate;
L0670 - indexes support expected queries;
L0671 - project data cannot be incorrectly linked across projects;
L0672 - ERD matches database/schema.sql;
L0673 - database-design.md matches ERD and schema;
L0674 - no unsupported business entity was invented;
L0675 - no secret is stored in the schema;
L0676 - unresolved requirements remain documented rather than silently solved;
L0677 - ERD contains no significant overlap or unreadable relationship lines.
